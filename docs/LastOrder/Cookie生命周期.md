# Cookie 生命周期（0.1.1 起）

0.1.1 起采用严格账号模型，平台验证的 UID 为必填且不可变的身份标识。LastOrder 负责检查和保存账号登录凭据；加密存储不会自行识别 Bilibili 会话是否已失效。0.1.5 增加 Windows 加密存储和 Android Keystore 支持的加密存储；0.2.3 及更早 macOS 使用逐条登录钥匙串；0.3.0 起 macOS 改用单一钥匙串主密钥和独立 `macos-vault-v1` 本地加密文件，账号身份验证规则保持不变，存储隔离及升级操作见 [macOS 加密存储](macOS加密存储.md)。

## 登录状态与检查时机

Cookie 的字段或保存时间不能保证服务端会话有效。运行时向固定 HTTPS 登录状态端点 `https://api.bilibili.com/x/web-interface/nav` 发送当前 Cookie，并只返回白名单状态、昵称和账号 UID，不转发原始响应或异常。

| 状态 | 判定 | 本地行为 |
| --- | --- | --- |
| 有效 `valid` | HTTP 成功，平台明确已登录并返回可验证的账号 UID | 记录检查时间，允许继续查询或分发 |
| 失效 `expired` | 平台明确返回未登录，例如业务码 `-101` | 标记需要重新登录、阻止新任务分发、删除旧 Cookie |
| 待确认 `unknown` | 断网、超时、HTTP 错误、限流、畸形或不明确的响应 | 保留凭据，提示稍后重试，阻止未验证的分发 |

应用正常启动后检查现有账号，运行期间每五分钟检查一次；账号页提供手动“检查登录”。读取场次和分发任务前再次检查，避免仅依赖上次检查结果。检查只表示当时有效，无法保证随后等待开售期间不会失效。

## 扫码自动检测与例行检查协调

自 0.3.1 起，打开登录或重新登录窗口后自动生成二维码，二维码显示后自动检查确认状态，不再提供扫码窗口中的“检测登录”按钮，也无需再点击“生成二维码”（0.3.0 及更早安装包仍保留原按钮）；账号列表中的“检查登录”和已有 Cookie 的“验证并保存”仍保留。

二维码状态检查与已登录账号的 Cookie 检查职责不同：

| 流程 | 检查对象 | 时机与结果 |
| --- | --- | --- |
| 二维码状态检查 | 当前二维码标识 | 正常情况下每次查询结束后等待 2 秒，再发起一次查询；同一会话不叠加请求 |
| 新凭据身份验证 | 扫码确认后取得的 Cookie | 保存前验证有效性与平台 UID；重新登录还须匹配原账号 UID |
| 已保存凭据检查 | 当前保存的 Cookie | 启动、每五分钟例行巡检、手动检查及读取场次或分发任务前检查 |

二维码状态可区分等待扫码、已扫码等待手机确认、确认成功和平台明确失效。过期只按平台响应判定，不用本地 180 秒计时推断过期；二维码过期与已保存 Cookie 失效没有对应关系。运行时明确返回可恢复的 `transient_error` 时，连续第一次失败等待 4 秒、第二次等待 8 秒后重试，第三次暂停并显示“重试连接”；点击后继续查询同一个二维码，由平台重新判断状态。正常查询结果会清除连续失败计数。安装问题、原生桥接超时、异常协议等无法确认调用是否正常结束的错误停止自动检查并提示重新生成，不继续自动排入请求；这些错误均不显示成二维码过期。若二维码已确认，但新 Cookie 的身份暂时无法验证，则不保存该候选凭据，提示重新扫码。二维码生成失败、扫码取消、二维码失效或新账号身份不匹配均不会由扫码流程清除原账号凭据。

扫码确认后的身份验证通过后，直接沿用账号新增或刷新流程，保存成功才关闭窗口；不为同一次成功再额外发起一次 `login_state`。本地保存失败保留窗口，已验证结果仅暂存内存，并提供“重试保存”；重试使用该结果，不再次轮询领取可能无法重复获取的 Cookie。保存完成前不能显示登录成功。关闭、切换登录方式或重新生成会清除待保存结果。二维码、二维码标识及待处理的成功结果只保留在本次会话内存中，不写普通配置或日志。

应用进入非前台状态时暂停发起后续二维码请求，回到前台后继续当前会话。已经发出的调用可能仍在运行；其当前会话成功结果只暂存内存，回到前台后继续处理，避免丢弃可能无法再次取得的确认结果。已经开始的本地保存完整完成，不因切换前后台中断；保存期间禁止关闭和切换方式，失败后恢复操作。关闭窗口、切换已有 Cookie 登录或重新生成二维码会废弃旧会话；之后迟到的旧响应不得保存账号、更新新二维码或关闭新的窗口。停止调度不等于立即中断底层网络请求。二维码数据不完整或图片无法解码时停止检查并提供重新生成。

活动扫码会话期间暂缓启动新的例行账号巡检，结束后合并补做被延后且已经到期的检查。例行检查按账号逐项启动，每项前重新确认是否暂停，不一次性将所有账号查询排入 Android 的串行运行时。已在途的账号检查正常收尾，仍用凭据版本和检查序号淘汰旧结果。刚通过身份验证的当前 Cookie 在五分钟内不重复例行检查；只有本次应用会话内确认有效、且凭据版本仍一致的结果可用于此跳过，不能只看 `lastChecked`（未知与失效检查也会更新时间），应用启动仍重新核验已保存账号。

暂缓仅作用于例行巡检，不跳过用户主动检查、读取场次或任务分发前的强制校验。旧 Cookie 检查被新凭据替换后淘汰时，不能用新账号的有效状态替它授权旧分发流程。登录更新仍不启动抢票，也不热更新已发送到 Sisters 的任务凭据。

## 存储与清理

普通元数据使用 schema 2，保存于 `state-v2.json`。0.2.3 及更早的账号 Cookie 存于 `v2.account.<本地账号ID>` 系统安全存储条目，含购票人信息的任务配置存于 `v2.task.<本地任务ID>`。0.3.0 起 macOS 将账号和任务的敏感内容保存在本地加密文件中，钥匙串仅保存一条应用主密钥，同一会话不再为每个账号、任务反复读取钥匙串；Windows/Android 仍使用原条目。任务配置始终不持久化 Cookie，校验与执行时在内存中使用关联账号的当前 Cookie。

macOS 新根目录为应用支持目录内的 `MisakaNetwork/macos-vault-v1`，其中的元数据仍使用 schema 2；旧根目录及逐条钥匙串凭据不被读取、迁移或清理。首次切换后本地机器、账号、任务、云资源记录和偏好均为空，需要重新配置。远端任务、订单和云资源不会因此消失：切换前先停止或等待任务结束，并在旧应用或云控制台核对、释放不再使用的资源。

0.3.0 的任务卡片改进在普通任务元数据中增加可选 `summary`，仅包含公开的演出名称、场次、票档、所选日期和数量。摘要由创建向导按实际选择提取，不读取或复制购票人、证件、联系人、电话、地址、Cookie 或上游配置中的 `detail`。没有摘要的任务仍显示原有名称、关联账号与开抢时间，并提示场次与票档未记录；不会从敏感配置推测摘要或触发任务重新分发。

明确失效后，先阻止继续使用该账号，再删除账号凭据并回读确认。账号行和任务关联不被删除，以便重新登录。加密存储读写或清理失败时明确提示，不能声称删除成功；可以再次检查重试清理。离线或平台异常不会触发此删除流程。macOS 删除账号时只更新密文中的对应记录，保留主密钥及其他资料；拒绝主密钥授权后需处理权限并重新打开应用，当前会话不因自动检查而重复触发授权。

直接使用系统安全存储的平台在删除前先读取同一命名空间的条目，不存在则直接成功，避免插件对已不存在条目的重复删除误报权限错误；macOS 新存储在核验密文后检查记录是否存在。两条路径均不吞掉读取或删除错误；删除现有条目后仍需回读确认，应用沙盒保持启用。

根据 1.0.0 前的研发版本规范，0.1.1 不读取或迁移 0.1.0 的 `state.json` 和旧钥匙串条目，也不从 Cookie 的 `DedeUserID` 推断账号身份。旧数据保留原样；升级后重新添加机器连接、登录账号、创建任务并部署新版 Sisters。

同一账号的凭据修改按序执行，并用检查序号与凭据版本识别过时结果。旧 Cookie 的检查即使在新登录后才返回，也不能删除或覆盖新 Cookie。多个账号并发检查时，元数据保存按序合并，避免互相覆盖。

## 重新登录

账号页的“重新登录”和创建任务窗口中的“重新登录此账号”打开同一个扫码流程，也可验证并导入已有 Cookie。新凭据必须先通过在线验证，取得平台 UID，再与原账号比较；昵称变化不会改变账号身份，扫描其他账号会被拒绝。

成功后更新原来保存的账号凭据，保留本地账号 ID、任务 ID 和场次选择。新建账号与重新登录均要求运行时确认的平台 UID；缺少身份或 UID 不匹配时拒绝保存。

重新登录不自动启动抢票、不改变已发往 Sisters 的执行。Sisters 持有提交时的凭据；同一任务 ID 携带不同 Cookie 或配置重新提交会被拒绝，并提示先查看旧执行，再新建任务分发。这样不会将登录更新误当成一次新的下单指令。
