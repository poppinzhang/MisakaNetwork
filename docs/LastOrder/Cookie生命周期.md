# Cookie 生命周期（0.1.1 起）

0.1.1 起采用严格账号模型，平台验证的 UID 为必填且不可变的身份标识。LastOrder 负责检查和保存账号登录凭据；系统安全存储负责加密与访问控制，不会自行识别 Bilibili 会话是否已失效。0.1.5 增加 Windows 加密存储和 Android Keystore 支持的加密存储；macOS 继续使用登录钥匙串，存储模型与身份验证规则不变。

## 登录状态与检查时机

Cookie 的字段或保存时间不能保证服务端会话有效。运行时向固定 HTTPS 登录状态端点 `https://api.bilibili.com/x/web-interface/nav` 发送当前 Cookie，并只返回白名单状态、昵称和账号 UID，不转发原始响应或异常。

| 状态 | 判定 | 本地行为 |
| --- | --- | --- |
| 有效 `valid` | HTTP 成功，平台明确已登录并返回可验证的账号 UID | 记录检查时间，允许继续查询或分发 |
| 失效 `expired` | 平台明确返回未登录，例如业务码 `-101` | 标记需要重新登录、阻止新任务分发、删除旧 Cookie |
| 待确认 `unknown` | 断网、超时、HTTP 错误、限流、畸形或不明确的响应 | 保留凭据，提示稍后重试，阻止未验证的分发 |

应用正常启动后检查现有账号，运行期间每五分钟检查一次；账号页提供手动“检查登录”。读取场次和分发任务前再次检查，避免仅依赖上次检查结果。检查只表示当时有效，无法保证随后等待开售期间不会失效。

## 存储与清理

普通元数据使用 schema 2，保存于 `state-v2.json`；账号 Cookie 存于 `v2.account.<本地账号ID>` 钥匙串条目，含购票人信息的任务配置存于 `v2.task.<本地任务ID>`。任务配置始终不持久化 Cookie，校验与执行时在内存中使用关联账号的当前 Cookie。

明确失效后，先阻止继续使用该账号，再删除账号凭据并回读确认。账号行和任务关联不被删除，以便重新登录。钥匙串读写或清理失败时明确提示，不能声称删除成功；可以再次检查重试清理。离线或平台异常不会触发此删除流程。

删除前先读取同一命名空间的条目，不存在则直接成功，避免 macOS 插件对已不存在条目的重复删除误报权限错误。这个检查不吞掉读取或删除错误；删除现有条目后仍需回读确认，应用沙盒保持启用。

根据 1.0.0 前的研发版本规范，0.1.1 不读取或迁移 0.1.0 的 `state.json` 和旧钥匙串条目，也不从 Cookie 的 `DedeUserID` 推断账号身份。旧数据保留原样；升级后重新添加机器连接、登录账号、创建任务并部署新版 Sisters。

同一账号的凭据修改按序执行，并用检查序号与凭据版本识别过时结果。旧 Cookie 的检查即使在新登录后才返回，也不能删除或覆盖新 Cookie。多个账号并发检查时，元数据保存按序合并，避免互相覆盖。

## 重新登录

账号页的“重新登录”和创建任务窗口中的“重新登录此账号”打开同一个扫码流程，也可验证并导入已有 Cookie。新凭据必须先通过在线验证，取得平台 UID，再与原账号比较；昵称变化不会改变账号身份，扫描其他账号会被拒绝。

成功后更新原来的钥匙串条目，保留本地账号 ID、任务 ID 和场次选择。新建账号与重新登录均要求运行时确认的平台 UID；缺少身份或 UID 不匹配时拒绝保存。

重新登录不自动启动抢票、不改变已发往 Sisters 的执行。Sisters 持有提交时的凭据；同一任务 ID 携带不同 Cookie 或配置重新提交会被拒绝，并提示先查看旧执行，再新建任务分发。这样不会将登录更新误当成一次新的下单指令。

## 验证范围

自动化测试使用虚构账号与模拟平台响应，覆盖有效/失效/未知三态、网络错误保留凭据、钥匙串删除失败、schema 与存储命名空间隔离、同账号刷新、账号不匹配、迟到检查结果、分发前阻断及界面重新登录入口。原生集成测试使用合成凭据验证真实钥匙串写入、读取、删除、重复删除与命名空间隔离；不使用真实用户 Cookie，不创建订单或执行支付。

历史结果见 [0.1.1 发布说明](../releases/0.1.1.md)，当前版本验证见 [0.1.6 交付记录](../releases/0.1.6.md)。
