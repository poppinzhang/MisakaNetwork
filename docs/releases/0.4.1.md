## 本版改动

- **修复 Windows Sisters 部署停在「上传并解压安装包」**：0.4.0 远程 Windows PowerShell 用 `[Console]::OpenStandardInput()` 读取上传数据；Win32-OpenSSH 的标准输入是重叠 I/O 命名管道，.NET Framework 控制台流在管道暂时读空后不再返回，约 2 分钟后被停滞检测中断，显示「上传或解压 Windows 部署包失败；当前版本未变更」。问题位于远程 Windows 一侧，从 Android、macOS 或 Windows 管理端部署都会受影响，写入私有配置的步骤同样修复。现通过内存定义的 `GetStdHandle`（设置 `PreserveSig`）取得继承句柄并以同步 `FileStream` 读取，不调用 `Add-Type` 编译代码，也不从可写临时目录加载 DLL。
- **上传压缩与连接保活**：Windows 上传改为 Deflate 最快级别压缩的 ZIP（以 Linux 包估算传输量由 104 MB 降至 42 MB）；上传、写入配置与自检阶段每 30 秒发送 SSH keepalive 并等待应答，服务器无响应时仍按停滞检测中断，切换服务前停止发送。
- **失败提示**：区分本地部署包读取失败、远程写入或解压失败（提示检查系统盘空间和安全软件拦截）与 SSH 连接中断，不转发远程原始错误。
- **统一版本与全平台重打包**：五种 LastOrder 与五种 Sisters 目标统一为 `0.4.1`；Android `arm64` / `amd64` 的 `versionCode` 分别为 `2014` / `4014`。Linux/macOS Sisters 与 LastOrder 界面没有功能变化，仍按统一发布约定重新构建。

本版不升级 biliTickerBuy 的版本、固定提交、导入白名单、锁定依赖、嵌入适配或运行参数，运行时只更新统一版本号；标准 HTTPS 验证、`standard` 下单策略、空第三方通知配置与禁止 Web UI/Gradio 的约束保持不变。问题根因、现场与验证细节见 [Windows Sisters](../Sisters/Windows支持.md#040-上传停滞问题)。

## 升级与使用注意

- **重新部署所有 Sisters**：安装 0.4.1 管理端后，在没有活跃抢票任务时将所有受控机器（含 Linux/macOS）重新部署为 `0.4.1`，防止 helper/runtime 版本校验拒绝旧包。重部署会停止该节点正在运行的任务，并清空内存任务历史和付款入口；操作前先核对订单。
- **数据无需重建**：账号、任务配置、云凭据与资源记录、macOS `macos-vault-v1` 存储格式均与 0.4.0 相同，无需重新登录或重建任务。
- **0.4.0 失败部署的残留**：每次失败的 0.4.0 Windows 部署会留下一个停在读取中的 `powershell.exe`（父进程 `cmd.exe`）及被占用的 0 字节 `payload.zip`。它们不妨碍重新部署；重启 Windows 或结束这些进程后，管理员可核对并删除 `%ProgramData%\MisakaNetwork\Sisters\releases` 下对应的未启用版本目录。
- **Android 覆盖安装**：沿用长期发布签名密钥，`versionCode` 从 `2013`/`4013` 递增为 `2014`/`4014`，可覆盖同签名正式版；测试签名 APK 需先卸载。Android 仍只管理任务，不在手机本机运行 Sisters。
- **macOS 与 Windows 签名**：macOS 仍为 ad-hoc 签名、未公证，首次打开新版访问主密钥时可能需要钥匙串授权；Windows 包仍不含 Authenticode 签名。
- **持续运行与订单核对**：关闭 LastOrder 不会停止远程 Sisters；取消和重新部署不能撤销票务平台已创建的订单，仍需在官方平台核对并付款。
