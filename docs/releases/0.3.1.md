## 变更

- **扫码登录自动检测**：打开登录或重新登录窗口后自动生成二维码，每次单次查询结束后等待 2 秒再检查，移除扫码窗口的「检测登录」按钮，无需再点击「生成二维码」；手机确认、账号身份验证及保存成功后自动完成登录。二维码过期仅按平台明确响应（`86038`）判断，不使用本地 180 秒截止时间；明确临时异常连续失败时按 4 秒、8 秒延迟重试，第三次暂停供「重试连接」；未知异常停止并提示重新生成；身份验证通过但本地保存失败时仅留在内存并提供「重试保存」，不重新轮询领取 Cookie。
- **登录会话与账号巡检协调**：活动扫码会话期间暂缓例行 Cookie 巡检，结束后合并补做到期账号，本次会话内刚验证有效的当前凭据不重复例行检查；手动检查、读取场次及分发前强制校验保留。前后台切换暂停与恢复新请求，当前会话成功结果仅暂存内存；关闭、切换已有 Cookie 或重新生成后废弃旧响应。重新登录仍核对原 UID，旧检查结果不能覆盖或删除新 Cookie；扫码 Cookie 扁平化前仅保留显式根域、根路径且未过期且无重名的候选。
- **修复 Android 扫码登录无法生成二维码**：Android 内嵌客户端仅携带 `qrcode` 8.2 与 `PyPNG`（不含 `Pillow`），此前 `qr_start` 调用 `qrcode` 默认工厂会先无条件导入 `Pillow`，导致 `0.3.0` 等 Android 安装包生成二维码失败并误报为网络/登录错误。现登录与付款二维码共用内存编码函数 `encode_qr_png`，按可用依赖显式选择 `PilImage` 或 `PyPNGImage`；编码组件缺失时返回固定错误 `qr_encoder_unavailable`（「内置二维码组件不完整，请重新安装此版本」）。
- **Android 依赖集 CI 回归检查与安全复核**：`verify.yml` 与 `package.yml` 的 Android 作业先按 `runtime/requirements-android.lock` 建立独立 Python 3.11 环境，断言包含 `qrcode` 与 `PyPNG` 且不含 `Pillow` 后再运行全部 runtime 测试。重新复核 `qr_poll` 单次查询适配、TLS 默认验证、禁止重定向与 `Set-Cookie` 作用域约束，上游快照、导入白名单、`standard` 下单参数、空通知与无 Web UI/Gradio 限制未改变。
- **统一版本与全平台重建**：所有组件、平台版本资源与四种内嵌 Sisters 部署包统一更新为 `0.3.1+11`。

## 升级影响与边界

- **Sisters 重新部署**：安装 `0.3.1` 后须将全部机器上的 Sisters 重新部署为 `0.3.1`（统一项目版本，控制端与部署器核对节点及运行时版本一致）；升级前先停止或等待现有任务完成，重部署会中断运行任务且不自动恢复。
- **Android 覆盖升级与登录修复**：沿用 `0.2.1`/`0.2.3`/`0.3.0` 长期发布密钥并提高构建号至 `11`，可直接覆盖升级上述正式签名版本；曾受 `0.3.0` Android 登录二维码生成失败影响的用户升级后可正常生成登录二维码。若曾安装 `0.2.0` 等测试签名 APK，仍需卸载旧版再安装（卸载会删除本地数据）。
- **macOS 存储目录与授权**：从 `0.3.0` 升级至 `0.3.1` 继续沿用 `macos-vault-v1` 独立加密资料目录；从 `0.2.3` 或更早版本首次升级仍会启用独立 `macos-vault-v1` 目录（不读取、迁移或删除旧资料，详见 [0.3.0 发布记录](0.3.0.md#升级影响与边界)）。因 macOS 仍为 ad-hoc 签名，更新应用版本后系统仍可能再次提示登录钥匙串授权。
- **签名与未实现能力**：macOS 未经 Apple 公证，Windows 未做 Authenticode 签名；Windows Sisters、自动付款、付款码主动刷新、跨节点自动取消、任务重启恢复与证书自动续期仍未实现，Android 后台同步不保证常驻。
