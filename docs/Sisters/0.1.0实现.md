# Sisters 0.1.0

Sisters 是接收 LastOrder 任务的 Go 命令行服务。本版本提供 macOS（15.0+）和 Linux（Ubuntu 24.04 LTS 同代，glibc 2.39+、GTK 3.24）实现，Linux 发布目标为 x64 与 arm64。Windows 不属于 0.1.0 交付范围。

## 启动与配置

```sh
sisters --version
sisters serve --config agent.json
```

配置模板见 `Sisters/config.example.json`。`cert`、`key`、`ca` 和 `runtime` 的相对路径均以配置文件目录为基准。`runtime` 必须是可直接执行的 biliTickerBuy bridge 文件，不接受 shell 命令或命令拼接。

| 配置项 | 含义与默认值 |
| --- | --- |
| `listen` | 监听地址，默认 `127.0.0.1:7443`；远程使用时由部署配置显式指定监听接口 |
| `cert` / `key` | 必填，服务端 PEM 证书与私钥 |
| `ca` | 必填，允许连接的客户端证书签发 CA |
| `runtime` | 必填，bridge 可执行文件路径 |
| `max_concurrency` | 同时运行的任务数，默认 2，范围 1–32 |
| `queue_capacity` | 等待队列容量，默认 64，范围 1–4096 |
| `history_capacity` | 内存任务记录容量，默认 1000，最大 10000；不得小于并发数与队列容量之和 |

只接受单个 JSON 配置对象，未知字段和非法容量会拒绝启动。建议限制配置与 TLS 私钥为当前服务用户可读。证书加载失败、地址无法监听等启动错误使用通用描述，不输出本地路径、用户名或证书内容。

## 通信与状态

服务只提供 gRPC over TLS，最低 TLS 1.2，支持 TLS 1.3。必须提供受配置 CA 信任的客户端证书；明文连接、无证书连接和不受信任的客户端证书都会被拒绝。证书是客户端访问该 Sisters 的授权凭据，0.1.0 不提供同一 CA 下的客户端角色划分。

协议定义在 `proto/misaka/v1/sisters.proto`：

- `GetStatus` 返回服务版本、biliTickerBuy 版本、平台、启动时间、最大并发数、运行环境可用性、是否支持开售时间（`supports_time_start`）、是否支持任务请求间隔（`supports_request_interval`，未发布）及内存任务记录。
- `SubmitTask` 接收任务 ID、名称、Cookie JSON、原 biliTickerBuy 配置 JSON，以及可选的开售时间 `time_start`（北京时间 `YYYY-MM-DDTHH:MM:SS`，空值立即开始）。格式错误返回 `InvalidArgument`；开售时间与载荷一起参与幂等摘要。旧版 Sisters 不认识该字段，会忽略它并立即开始，因此客户端只向声明 `supports_time_start` 的 Sisters 发送定时任务。
- 未发布的 `request_interval_ms` 指定本任务的抢票请求间隔，范围为 100–60000 整数毫秒；零值或省略使用 1000 毫秒。Sisters 在启动运行时前校验并转交该值，生效间隔参与幂等摘要，因此省略与显式指定 1000 毫秒属于同一载荷，改变间隔必须新建任务。LastOrder 分发前要求机器声明 `supports_request_interval`，旧机器须重新部署，避免其忽略间隔配置。每轮下单尝试上限由内嵌运行时固定为 40 次，不提供协议或服务配置项。
- `CancelTask` 取消排队或运行中的任务，重复取消返回已有终态。

运行环境检查真实执行 bridge 的 `ping`，验证它报告 `protocol: 1`、`ready: true` 和合法版本号；只检查文件存在或进程退出码为零都不够。检查最多执行 5 秒，结果缓存 2 秒，不访问票务平台。运行环境尚未安装或依赖损坏时，服务仍可供 LastOrder 查询，但拒绝接收新任务。

错误映射包括：非法输入 `InvalidArgument`、相同 ID 不同载荷 `AlreadyExists`、队列满 `ResourceExhausted`、运行环境不可用 `FailedPrecondition`、未知任务 `NotFound` 和服务关闭 `Unavailable`。客户端应定时轮询并设置 RPC 超时。大量历史记录可能超过 gRPC 默认 4 MiB 接收限制，客户端应将最大接收响应设置为 64 MiB；服务请求大小限制为 3 MiB。

## 调度、取消与幂等

任务依次经过 `QUEUED`、`RUNNING` 和 `SUCCEEDED` / `FAILED` / `CANCELLED`。等待队列采用 FIFO，多 worker 并发执行，每个任务单独启动一个 bridge 进程。运行任务与排队任务互不共享 Cookie 或配置。队列已满时不接收新的不同任务，取消排队任务会立即释放队列位置。

相同 ID、名称和载荷重发只返回现有记录，不会重复执行；相同 ID 携带不同名称或载荷则拒绝。摘要会压缩 JSON 的无意义空白，但不会对对象键排序。历史满时淘汰最早登记且已经完成进程清理的终态记录；记录被淘汰或服务重启后，幂等保护不再保留，因此调用端应使用不复用的任务 ID，并在不确定结果时先查询订单。

取消运行任务时，macOS/Linux 杀死整个进程组，以同时终止 bridge 及其子进程。未发布源码新增 Windows 10+ x64：通过 Job Object 取消任务进程树，并提供 SCM 后台服务入口；部署、权限和验证边界见 [Windows Sisters](Windows支持.md)。源码未发布的付款回显同时处理终态竞态：如果已经读到合法且明确确认订单的最终结果，无协议错误时即使随后的取消导致进程非零退出，仍保留成功状态和付款信息；普通进度与失败/取消结果不能覆盖已取消状态。停止 Sisters 会取消全部任务并等待运行进程退出。取消只能停止后续动作，不能撤销已经由票务平台创建的订单。

## biliTickerBuy bridge

每个进程从标准输入读取一行 JSON：

```json
{"op":"run","params":{"cookies":[],"config":{},"runtime_options":{"interval":1000}}}
```

源码未发布的任务始终在 `runtime_options.interval` 中传递生效的整数毫秒间隔。设置开售时间时，同一对象另带 `"time_start":"2026-11-20T20:00:00"`；空值不传递。

Cookie 支持 bridge 定义的数组与对象形式。标准输出为 JSONL：`type: progress` 表示进度；`type: result` 表示终态。通常要求进程正常退出、恰好返回一个合法终态、`ok: true` 且 `data.status` 为 `succeeded` 或 `duplicate_order`，才标记成功；唯一的取消例外见上文，不放宽终态与协议校验。`completed` 表示未确认下单，作为失败展示；空输出、仅退出码为零、非法 JSON、重复终态及普通非零退出码都不会伪报成功。

0.1.0 仅提示用户到哔哩哔哩订单页确认并支付。源码中的付款码回显改动见下节，尚未包含于当前 0.2.3 安装包。

## 付款结果回传（未发布）

运行时最终结果确认 `succeeded` / `duplicate_order` 且包含合法订单号时，Sisters 才填充 `TaskStatus.payment`。`OrderPayment` 包含 `order_id`、`order_detail_url`、可选 `payment_code_url` 与 `captured_unix_ms`；Go 层独立校验订单号及支付内容，并从订单号构造固定官方详情链接。缺少支付码或支付内容不在白名单时保留订单详情；缺少合法订单号时不构造付款结果。时间只在接收结果时记录，重复状态查询不改变。

付款结果通过既有 mTLS 返回，不进入 `message`、`events`、标准错误或普通文件，任务秘密仍在结束时清除，不为未来刷新保留 Cookie。返回状态时深拷贝嵌套付款结果，避免调用方修改内部记录。进程协议失败、未确认终态或实际取消结果不会产生付款入口；用户取消与合法最终成功结果竞争时保留已确认订单，避免把平台已经创建的订单隐藏。

服务仍按任务 ID 独立保存结果；LastOrder 负责将多个节点回报的相同账号、同一订单聚合显示。节点重启、重部署或历史淘汰后支付结果随任务记录丢失，不恢复、不自动取新码。完整字段约束与边界见[付款码回显](../付款码回显.md)。

## 数据与隐私

Cookie 和配置仅通过 mTLS 请求与进程标准输入传递，不写入任务文件、不放在进程参数或环境变量中。排队 payload 在任务结束或排队取消后从队列记录清除；Go 运行时和操作系统的内存管理不保证所有历史内存副本立即擦除。

任务状态的消息与事件只使用预定义的中文进度描述，按 bridge 的阶段代码区分等待开票、准备订单、创建订单与请求冷却。当前状态行可附带倒计时或尝试次数，这些数字只来自 bridge 校验过的整数；事件记录只保存固定的阶段描述，每秒更新的倒计时不会产生新事件。消息与事件不转发 bridge 的任意日志、错误字符串、订单 URL 或 Cookie；未发布的付款信息仅通过独立 `payment` 字段返回。标准错误直接丢弃。每项任务最多保留 64 个事件，相邻重复进度合并。调用者指定的任务名称用于界面显示，应避免填写账号、Cookie 等私密信息。

任务历史不持久化，服务重启后为空，也不会自动恢复中断任务。操作系统异常退出与远程网络中断不等于票务操作被撤销，用户应先核对订单再重发任务。

## 开发与验证

需要 Go 1.26 或项目 `go.mod` 声明的兼容工具链。从项目根目录运行：

```sh
go test -race ./Sisters/...
go build -o build/sisters ./Sisters/cmd/sisters
```

测试覆盖 mTLS 合法连接与拒绝场景、配置校验、并发上限、队列容量、幂等冲突、请求间隔默认值/上下界/非法值/运行时转交/幂等冲突、能力声明、排队及运行取消、服务停止、任务历史与事件边界、敏感输出隔离、真实子进程协议、运行环境检查和进程组取消。测试使用本地假 bridge 和临时证书，不向票务平台发送购买请求。发布前还需遵循项目打包文档运行全项目测试及各目标平台验证。
