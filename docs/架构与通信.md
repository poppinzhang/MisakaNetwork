# 0.3.1 架构与通信

LastOrder 是 Flutter macOS / Windows / Android 管控端；Sisters 是 Go 命令行服务；内嵌 Python 运行时对接 biliTickerBuy 2.15.18。平台任务由账号 Cookie 和已选择的场次、票档、购票人、地址以及开售时间组成。界面不会在保存任务时执行抢票。分发后，Sisters 按开售时间（北京时间，默认取所选票档的起售时间）倒计时再开始；未设置开售时间时立即开始。分发定时任务前，LastOrder 会实时确认目标 Sisters 支持开售时间（`supports_time_start`），旧版本会被拒绝并提示重新部署，以免忽略开售时间而立即开抢。

## 连接与数据

`proto/misaka/v1/sisters.proto` 定义 `GetStatus`、`SubmitTask`、`CancelTask`。全部使用双向 TLS：LastOrder 验证 CA 与服务器名称，Sisters 验证同一控制端 CA 签发的客户端证书。拒绝明文与未受信任客户端，不提供跳过证书验证的入口。

控制端首次使用生成独立 ECDSA CA 和客户端证书。CA 有效期五年，客户端与节点证书有效期一年。CA 私钥仅保留在控制端应用私有目录；远程仅收到节点证书、节点私钥和 CA 公钥。目录权限 0700，密钥权限 0600。首版不含自动续期、证书撤销列表或多人授权体系，接近到期前需要维护身份并重新部署。不要删除控制端证书目录，否则既有 Sisters 将无法信任新控制端。

账号 Cookie 和含购票人信息的任务配置使用加密存储。0.2.3 及更早使用 macOS 登录钥匙串、Windows 加密存储、Android Keystore 支持的加密存储。0.3.0 起 macOS 改为单一钥匙串主密钥保护本地 AES-256-GCM 密文，覆盖账号、任务、云凭据和云部署密钥，同一会话复用主密钥；Windows/Android 不变。macOS 应用沙盒保持开启；Windows 文件使用私有 DACL，Android 禁止备份并使用应用私有目录。普通状态文件仅保存机器连接资料、账号名称、任务名称与引用。Sisters 仅在内存中持有任务秘密，通过标准输入交给独立 runtime 子进程。子进程进度只转发白名单结构化状态，原始上游日志不会进入管控界面。

schema 2 元数据另保存必填账号 UID、登录状态和检查时间；任务配置不保存 Cookie 副本，只在校验与执行时从账号凭据填入。只有平台明确未登录才清除保存的账号凭据，网络异常保留凭据并暂停新分发；重新登录核对 UID 后更新原账号。0.1.1 使用 `state-v2.json` 与 `v2.` 安全存储命名空间，不读取或迁移 0.1.0 数据。0.3.0 起 macOS 使用独立 `macos-vault-v1` 目录，并隔离元数据、PKI 与导入证书；不读取、迁移、删除旧资料，需重新配置和部署机器。切换前须处理远端执行并核对旧云资源，避免丢失本地执行和资源关联后误重复操作。存储格式和失败边界见 [macOS 加密存储](LastOrder/macOS加密存储.md)，账号流程与现有执行的边界见 [Cookie 生命周期](LastOrder/Cookie生命周期.md)。

## 任务语义

0.3.0 新增任务请求间隔：LastOrder 创建时按整数毫秒保存，范围 `100`–`60000`、默认 `1000`，通过 `TaskRequest.request_interval_ms` 发送。Sisters 将协议缺省值 `0` 解析为默认值，拒绝其他越界值，并把实际间隔写入 `runtime_options.interval`、计入任务幂等摘要。每次分发前，LastOrder 实时查询 `supports_request_interval`，未声明支持时要求重新部署；定时任务仍须支持 `supports_time_start`。内嵌运行时将每轮下单尝试固定为 `40`，不接受调用方配置；每轮上限不是任务总尝试上限，请求节奏还包含响应耗时和冷却逻辑。修改间隔需创建新任务，已经分发的执行不热更新。使用本版本时须同步重新部署 Sisters。

同一任务可以分发到多台机器，每台机器可接收多任务。协议中的任务 ID 是一次执行的幂等键；同一 ID 和相同载荷返回已有结果，不会再次下单，重复 ID 携带不同内容会被拒绝。Sisters 只在内存中保存幂等记录，重启或淘汰历史后可能把同一 ID 当作新执行，因此调用端不能把记录缺失当作结束确认。

0.3.0 起 LastOrder 将任务配置与每台机器的执行记录分开：首轮执行使用任务配置 ID，确认成功、失败或取消后再次主动分发生成新的执行 ID，旧结果仍关联原任务。每轮先保存执行意图，再发送请求；同一任务在同一机器上存在未结束或结果未知的执行时禁止重复提交。只有确认未发送或服务端明确拒绝时才撤销新意图，网络异常或响应丢失不自动补发；取消响应的终态立即参与计数，旧轮询不能将其回退为执行中。具体存储与回归范围见 [执行结束与重新分发](LastOrder/0.1.0实现.md#执行结束与重新分发未发布)。0.2.3 及更早版本仍通过永久提交记录保护同一任务，重新执行需创建新任务。

各 Sisters 独立执行，没有跨机器分布式锁，也不会在某节点成功后自动取消其它节点；用户可在监控页取消其余任务。

Sisters 默认同时运行两个任务、最多排队 64 个、保留 1000 个任务记录，每任务最多 64 条事件。状态为排队、运行、成功、失败、取消。只有上游明确回传 `succeeded` 或 `duplicate_order` 才显示订单确认提示；进程正常退出或 `completed` 不代表已抢到票。支付由用户在哔哩哔哩订单页完成。

LastOrder 每五秒查询状态，失败会显示连接错误和最近一次状态；恢复网络后自动继续查询。关闭 LastOrder 不会终止远程任务。Sisters 重启会结束运行进程并清空内存任务记录，不自动重放任务；重新部署前应先取消或等待现有任务完成。

## 付款码回显

`TaskStatus.payment = 7` 附带可选 `OrderPayment`（订单号、固定订单详情 URL、受限支付内容与获取时间）。Sisters 只从合法最终成功结果构造该字段；Python、Go、Dart 分别校验，不把任意上游 URL、日志或 Cookie 当作支付信息透传。仍使用既有双向 TLS，无新增服务端口或 Web UI。LastOrder 通过本机内嵌运行时把支付内容编码成 PNG，用户主动打开二维码或官方订单页。

LastOrder 按本地账号 UID 与订单号合并来自多个节点、多个任务的相同订单，保留来源信息；不同账号或不同订单不合并，缺少本地账号/任务关联时不显示具体支付入口。展示去重与任务提交幂等是独立规则，不取消其他节点，也不自动付款。无付款码时保留官方详情入口，缺少订单号则仅保留核对提示。

付款数据只在内存保留，不加入普通状态文件或事件日志；Sisters 重启、重部署或历史淘汰可能使其丢失，LastOrder 重新打开只能再次读取节点仍保留的结果。当前没有二维码刷新、支付状态查询或有效期保证。字段约束、敏感数据流及验证范围见[付款码回显](付款码回显.md)。使用时需确保 LastOrder 与 Sisters 均已更新至 0.3.0。

## 部署

LastOrder 桌面端通过内嵌 `misakactl` 辅助进程连接 SSH，Android 通过 Go JNI 库复用相同部署实现。支持密码或所选私钥；密码仅在本次部署的内存中使用。0.3.0 的后台部署由控制器持有私钥临时副本，成功或失败后清理，关闭添加窗口不会提前删除；应用中途退出遗留的副本在下次启动时清理，移除机器时一并删除其导入的证书与私钥副本。Android 选择器复制到应用缓存的明文副本在导入后立即删除。0.2.3 及更早首次连接由用户核对 SHA-256 主机指纹；0.3.0 起改为首次使用时信任（TOFU），控制器自动保存首次探测的指纹，再携带固定指纹继续部署。保存失败或响应异常时停止；已保存指纹在重试和重新部署时严格验证，不接受静默更换。此方式依赖首次连接所见主机身份，不提供来自管理员或云助手的独立真实性证明，后续 gRPC 双向 TLS 验证不变。云主机卡片的「部署 Sisters」使用安全存储中的内置 SSH 身份，私钥直接通过标准输入或 Android 原生桥接交给 Go 在内存中解析，不建立明文文件副本；该流程执行相同的首次指纹保存、固定指纹验证和部署检查。

0.3.0 的机器添加流程先保存待部署记录，再从列表独立执行各台部署，支持继续添加不同地址的机器；重复地址的新部署在连接之前拒绝。进度按传包字节和部署阶段估算，首次指纹保存与后续验证自动完成，不再提供核对窗口或等待确认阶段。失败保留原记录供重试；应用中断后不自动恢复，待核查机器不得分发任务。状态、重复地址与凭据的具体规则见 [后台部署与进度](LastOrder/0.1.0实现.md#后台部署与进度未发布)。

辅助进程检测 Linux/macOS 和 amd64/arm64，选择应用内对应的完整离线包。部署包包含 Sisters、Python 解释器、biliTickerBuy 及依赖，不在远程下载程序。Linux 要求 glibc 2.39+，使用 systemd 用户服务；macOS 要求 15.0+，使用 launchd 用户域（`user/<uid>`）：服务描述声明 `LimitLoadToSessionType=Background`，图形登录时不会再在 `gui/<uid>` 域起一份实例；停止、重新部署和回滚都会同时清理两个域中的旧实例。用户域在该账号登录（图形或 SSH）后才存在。没有 linger 的 Linux 账号在最后一个会话结束后，systemd 会停止其用户服务，因此部署在上传之前先检查远程账号是否已开启 linger：未开启时以该账号身份尝试 `loginctl enable-linger`，是否允许取决于系统 polkit 策略。普通 SSH 部署不调用 sudo。腾讯云内置密钥部署显式启用一项受限操作：仅当前 `ubuntu` 账号在上述尝试后仍未开启时，执行 `sudo -n loginctl enable-linger ubuntu`，随后重新查询本账号的 linger 状态；不启动 sudo shell、不请求密码、不修改其他账号，也不用于部署程序本身。未获非交互授权或复查仍失败时，在上传程序之前停止，并提示管理员执行 `sudo loginctl enable-linger <用户名>`。远程用户须已启用 SSH 并具备用户服务运行条件，且控制端可连接所设 gRPC 端口（0.2.0 起默认 20001）。

默认端口 `20001` 致敬 Last Order（最后之作）的第 20001 号身份。它是可修改的项目默认值，不是 gRPC 或 TLS 的协议要求。新建机器和未提供端口的部署请求使用此值；已保存机器的显式端口保持原样。切换既有机器的端口时，需修改部署表单中的 gRPC 端口并重新部署，同步放行新的 TCP 端口；自行维护的 Sisters 则需同时更新服务监听地址与 LastOrder 连接配置。

部署先上传独立版本目录并执行自检，再切换 `current` 链接和启动服务。所有远程命令都交给 `/bin/sh` 执行，不依赖远程账号的登录 shell（bash、zsh、fish、csh/tcsh 均可）；登录 shell 启动文件向标准输出打印的内容也不会干扰结果解析。SSH 错误分别显示主机指纹不匹配、认证被拒绝、握手超时或其他握手未完成；不转发服务端原始错误，也不把网络中断一律解释为凭据错误。SSH 握手限 30 秒；之后按进度判断连接是否中断：任一方向 2 分钟没有数据才视为断开，所以慢速但仍在推进的上传可以继续。上传与自检最多 15 分钟，超时即中止，当前版本不变。切换后的健康检查有独立的 30 秒窗口；未通过时停止新服务并恢复旧版本，首次部署则停止并移除新服务。回滚结果如实报告：任何一步失败都会提示"回滚未完成"，不会声称已恢复。经 SSH 隧道的健康检查通过后，部署还会从本机直接连接 `主机:gRPC 端口` 做一次 mTLS 检查，并固定新签发的证书；这正是 LastOrder 之后实际走的路径。直连失败时部署仍算成功、不会回滚，但会提示确认防火墙或安全组已放行该 TCP 端口。LastOrder 为部署请求最多等待 30 分钟。重部署使用相同控制端 CA，更新节点证书及打包的完整运行时。

## 当前平台边界

0.1.5 增加 LastOrder Windows 与 Android 实现，Sisters 仍为 Linux/macOS 四种目标。实际安装包状态见 [发布记录](releases/0.3.1.md)，实现细节见 [Windows 与 Android](LastOrder/Windows与Android.md)。Linux 服务本身不依赖图形界面，支持 Ubuntu 24.04 同代 glibc 发行版。本轮没有真实账号登录和下单验证，也没有生产远程 SSH 主机验收；自动化验证不代表平台出票保证。
