# 0.2.3 架构与通信

LastOrder 是 Flutter macOS / Windows / Android 管控端；Sisters 是 Go 命令行服务；内嵌 Python 运行时对接 biliTickerBuy 2.15.18。平台任务由账号 Cookie 和已选择的场次、票档、购票人、地址以及开售时间组成。界面不会在保存任务时执行抢票。分发后，Sisters 按开售时间（北京时间，默认取所选票档的起售时间）倒计时再开始；未设置开售时间时立即开始。分发定时任务前，LastOrder 会实时确认目标 Sisters 支持开售时间（`supports_time_start`），旧版本会被拒绝并提示重新部署，以免忽略开售时间而立即开抢。

## 连接与数据

`proto/misaka/v1/sisters.proto` 定义 `GetStatus`、`SubmitTask`、`CancelTask`。全部使用双向 TLS：LastOrder 验证 CA 与服务器名称，Sisters 验证同一控制端 CA 签发的客户端证书。拒绝明文与未受信任客户端，不提供跳过证书验证的入口。

控制端首次使用生成独立 ECDSA CA 和客户端证书。CA 有效期五年，客户端与节点证书有效期一年。CA 私钥仅保留在控制端应用私有目录；远程仅收到节点证书、节点私钥和 CA 公钥。目录权限 0700，密钥权限 0600。首版不含自动续期、证书撤销列表或多人授权体系，接近到期前需要维护身份并重新部署。不要删除控制端证书目录，否则既有 Sisters 将无法信任新控制端。

账号 Cookie 和含购票人信息的任务配置使用系统安全存储：macOS 登录钥匙串、Windows 加密存储、Android Keystore 支持的加密存储。macOS 应用沙盒保持开启；Windows 文件使用私有 DACL，Android 禁止备份并使用应用私有目录。普通状态文件仅保存机器连接资料、账号名称、任务名称与引用。Sisters 仅在内存中持有任务秘密，通过标准输入交给独立 runtime 子进程。子进程进度只转发白名单结构化状态，原始上游日志不会进入管控界面。

schema 2 元数据另保存必填账号 UID、登录状态和检查时间；任务配置不保存 Cookie 副本，只在校验与执行时从账号凭据填入。只有平台明确未登录才清除钥匙串凭据，网络异常保留凭据并暂停新分发；重新登录核对 UID 后更新原账号。0.1.1 使用 `state-v2.json` 与 `v2.` 钥匙串命名空间，不读取或迁移 0.1.0 数据。流程与现有执行的边界见 [Cookie 生命周期](LastOrder/Cookie生命周期.md)。

## 任务语义

同一任务可以分发到多台机器，每台机器可接收多任务。任务 ID 是幂等键；同一 ID 和相同载荷返回已有任务，不会再次下单。重复 ID 携带不同内容会被拒绝。已终止的任务需要创建新任务后才能重新执行。Sisters 只在内存中保存幂等记录，重启或淘汰历史后会把同一 ID 当作新任务；因此 LastOrder 在本地元数据中记录每个任务已提交到的机器（包括轮询时在远端发现的同 ID 任务），同一任务不会再次提交给已接收它的机器。提交结果不确定（如响应丢失）时，重试仍使用同一 ID，由 Sisters 去重。各 Sisters 独立执行，首版没有跨机器分布式锁，也不会在某节点成功后自动取消其它节点；用户可在监控页取消其余任务。

Sisters 默认同时运行两个任务、最多排队 64 个、保留 1000 个任务记录，每任务最多 64 条事件。状态为排队、运行、成功、失败、取消。只有上游明确回传 `succeeded` 或 `duplicate_order` 才显示订单确认提示；进程正常退出或 `completed` 不代表已抢到票。支付由用户在哔哩哔哩订单页完成。

LastOrder 每五秒查询状态，失败会显示连接错误和最近一次状态；恢复网络后自动继续查询。关闭 LastOrder 不会终止远程任务。Sisters 重启会结束运行进程并清空内存任务记录，不自动重放任务；重新部署前应先取消或等待现有任务完成。

## 部署

LastOrder 桌面端通过内嵌 `misakactl` 辅助进程连接 SSH，Android 通过 Go JNI 库复用相同部署实现。支持密码或所选私钥；密码仅在内存中使用，私钥临时副本在部署窗口关闭时清理；应用中途退出遗留的副本在下次启动时清理，移除机器时一并删除其导入的证书与私钥副本。Android 选择器复制到应用缓存的明文副本在导入后立即删除。首次连接必须由用户核对 SHA-256 主机指纹，后续连接严格验证已保存指纹。

辅助进程检测 Linux/macOS 和 amd64/arm64，选择应用内对应的完整离线包。部署包包含 Sisters、Python 解释器、biliTickerBuy 及依赖，不在远程下载程序。Linux 要求 glibc 2.39+，使用 systemd 用户服务；macOS 要求 15.0+，使用 launchd 用户域（`user/<uid>`）：服务描述声明 `LimitLoadToSessionType=Background`，图形登录时不会再在 `gui/<uid>` 域起一份实例；停止、重新部署和回滚都会同时清理两个域中的旧实例。用户域在该账号登录（图形或 SSH）后才存在。没有 linger 的 Linux 账号在最后一个会话结束后，systemd 会停止其用户服务，因此部署在上传之前先检查远程账号是否已开启 linger：未开启时以该账号身份尝试 `loginctl enable-linger`（是否允许取决于系统 polkit 策略，部署器不会提权）；仍未开启则在改动远端之前停止部署，并提示管理员执行 `sudo loginctl enable-linger <用户名>`。远程用户须已启用 SSH 并具备用户服务运行条件，且控制端可连接所设 gRPC 端口（0.2.0 起默认 20001）。

默认端口 `20001` 致敬 Last Order（最后之作）的第 20001 号身份。它是可修改的项目默认值，不是 gRPC 或 TLS 的协议要求。新建机器和未提供端口的部署请求使用此值；已保存机器的显式端口保持原样。切换既有机器的端口时，需修改部署表单中的 gRPC 端口并重新部署，同步放行新的 TCP 端口；自行维护的 Sisters 则需同时更新服务监听地址与 LastOrder 连接配置。

部署先上传独立版本目录并执行自检，再切换 `current` 链接和启动服务。所有远程命令都交给 `/bin/sh` 执行，不依赖远程账号的登录 shell（bash、zsh、fish、csh/tcsh 均可）；登录 shell 启动文件向标准输出打印的内容也不会干扰结果解析。SSH 握手限 30 秒；之后按进度判断连接是否中断：任一方向 2 分钟没有数据才视为断开，所以慢速但仍在推进的上传可以继续。上传与自检最多 15 分钟，超时即中止，当前版本不变。切换后的健康检查有独立的 30 秒窗口；未通过时停止新服务并恢复旧版本，首次部署则停止并移除新服务。回滚结果如实报告：任何一步失败都会提示"回滚未完成"，不会声称已恢复。经 SSH 隧道的健康检查通过后，部署还会从本机直接连接 `主机:gRPC 端口` 做一次 mTLS 检查，并固定新签发的证书；这正是 LastOrder 之后实际走的路径。直连失败时部署仍算成功、不会回滚，但会提示确认防火墙或安全组已放行该 TCP 端口。LastOrder 为部署请求最多等待 30 分钟。重部署使用相同控制端 CA，更新节点证书及打包的完整运行时。

## 当前平台边界

0.1.5 增加 LastOrder Windows 与 Android 实现，Sisters 仍为 Linux/macOS 四种目标。实际安装包状态见 [交付记录](releases/0.2.3.md)，实现细节见 [Windows 与 Android](LastOrder/Windows与Android.md)。Linux 服务本身不依赖图形界面，支持 Ubuntu 24.04 同代 glibc 发行版。本轮没有真实账号登录和下单验证，也没有生产远程 SSH 主机验收；自动化验证不代表平台出票保证。
