# 付款码回显（未发布）

本功能接通已有订单的支付信息回传，在 LastOrder 中展示付款二维码，并提供官方订单详情页作为兜底。当前仅为源码中的未发布改动，0.2.3 已交付安装包不包含此功能；未调整项目版本号、biliTickerBuy 固定提交或依赖锁定。

## 用户操作与范围

Sisters 确认 `succeeded` 或 `duplicate_order` 并取得合法订单号后，LastOrder 在「任务监控」展示对应订单。用户可点击「查看付款二维码」，用支付应用扫码核对并确认付款；「打开订单详情」交给系统浏览器，可能需要登录与抢票任务相同的哔哩哔哩账号。Android 在同一部手机上不便扫码时，可使用订单详情入口。

二维码由用户主动打开，五秒状态轮询和多个节点的相同回报不会自动重复弹窗。二维码不存在、格式不支持或本地生成失败时，仍保留已创建订单及订单详情入口，不把取码失败视为抢票失败，不因此重新提交抢票任务。

界面显示的是节点取得的历史支付信息。订单已创建、已有订单、二维码可显示都不代表已经付款或出票；免费订单也可能没有付款码。此版不刷新付款码、不查询支付状态，不提供二维码有效期倒计时，也不自动付款。应在官方订单页核对最终状态，无法扫码时及时转到订单页处理。

## 数据路径

1. Sisters 内嵌运行时沿用 `standard` 下单流程。上游成功响应提供 `orderId`，已有的 `getPayParam` 请求尝试取得 `code_url`。
2. `runtime/bridge.py` 从结构化 state 取订单与支付字段，完成校验，随 `run` 的最终 result 回传；普通 progress 和原始日志不承载支付内容。
3. Sisters 解析最终结果，独立重做校验，只在确认成功且订单号有效时写入 `TaskStatus.payment`；通过现有 mTLS gRPC 返回。
4. LastOrder 再次校验支付内容，并关联本地任务和账号后聚合展示。需要二维码时调用本机内嵌运行时的 `payment_qr`，仅在内存生成 PNG，不请求平台或支付网站。

固定上游的 `payment_code_url` 才是付款二维码内容；`payment_qr_url` 实际是订单详情页链接，不能按字段名把它当作二维码图片或直接付款码。无需在 Sisters 上启动图形界面、截图、开启上游 Web UI 或接入第三方通知。

## 字段与校验

公共协议为 `OrderPayment`，附在 `TaskStatus.payment = 7`：

| 字段 | 来源与约束 |
| --- | --- |
| `order_id` | ASCII 正整数，1–80 位，不允许前导零、符号、空白或其他字符 |
| `order_detail_url` | 根据合法订单号构造 `https://show.bilibili.com/platform/orderDetail.html?order_id=<order_id>`，不信任上游任意详情链接 |
| `payment_code_url` | 可选；仅允许下表所列完整字符串格式 |
| `captured_unix_ms` | Sisters 接收最终支付结果时记录的时间；重复查询不更新，不代表支付码的有效期或付款完成时间 |

首版支付内容采用完整字符串匹配，长度最多 2048 个 ASCII 字符；其中 token 为 1–512 个 `[A-Za-z0-9_-]` 字符：

| 类型 | 允许格式 |
| --- | --- |
| 微信 | `weixin://wxpay/bizpayurl?pr=<token>` |
| 支付宝 | `https://qr.alipay.com/<token>` |

不接受其他 scheme、主机、端口、用户名密码、片段、额外 query、百分号编码、空白、控制字符或 Unicode 近似字符。无法识别的支付内容被丢弃，合法订单号仍提供固定详情入口。详情入口与支付内容分开处理：付款 payload 仅编码为二维码，不作为任意浏览器跳转目标；用户点击订单详情时只打开由订单号生成的官方 HTTPS 地址。

这些格式来自固定上游付款测试样例及支付厂商文档中的二维码内容形式。支付宝官方[沙盒手册](https://os.alipayobjects.com/rmsportal/qzepRfDMREmzZQHMwXai.pdf)包含 `https://qr.alipay.com/` 形式；该资料仅作为格式依据，其历史沙盒有效期和支付流程不能直接套用到会员购订单。允许某种格式不表示已经验证会员购当前一定返回该格式，也不保证该链接的收款对象或业务状态；用户仍需在支付应用确认订单与金额。遇到其他合法格式时，后续应补充来源核查和离线回归后再扩展白名单，不放开任意 URL。

`payment_qr` 的请求为 `{"op":"payment_qr","params":{"payment_code_url":"<已校验内容>"}}`，成功只返回 `qr_png_base64`。桌面与 Android 复用同一校验和内存编码实现，使用已有二维码依赖；不新增请求支付参数、刷新或查询订单状态的操作。非法内容和编码错误只输出固定错误，不回显输入。

## 多节点去重与状态边界

LastOrder 使用本地任务所关联账号的 UID 与合法订单号作为订单聚合键。相同账号在多个 Sisters、多个任务中回报同一订单时，只显示一份订单及其来源节点、任务；不同账号或不同订单不合并，也不按任务名称推测身份。找不到对应本地任务或账号时不展示具体支付入口，仍保留原任务状态提示，用户应自行到平台核对。

同一订单存在多个回报时，优先选择含合法付款码的记录，避免另一个节点的无码结果覆盖已有付款码；有多个合法码时按节点记录的获取时间从新到旧选择，时间相同时按来源键稳定选择。来源列表合并并去重，重复轮询或返回顺序变化不增加订单卡。这里的选择规则不证明所选码仍有效，节点时钟也不作为平台到期依据。

订单聚合只改变付款信息展示，不替代任务 ID 的幂等机制，不取消其他节点，也不阻止平台产生不同订单。`duplicate_order` 不保证带有订单号：固定上游只有部分已有未完成订单路径会尝试取码。缺少订单号时不构造订单或付款码，继续提示用户核对平台订单。

只有符合运行时协议的最终成功结果才能附带支付信息。中间进度出现成功字样、`completed`、普通非零退出、无效输出、失败或实际取消的运行结果，都不能单独产生可付款订单卡。用户取消与最终成功结果竞争时，若已经读到合法确认订单的最终帧且无协议错误，即使后续取消导致进程非零退出，仍保留成功状态和付款信息；取消只能停止后续动作，不能撤销平台已创建的订单。

支付结果只在 Sisters 任务记录和 LastOrder 当前状态的内存中保存，不写入普通状态文件或事件日志。关闭再打开 LastOrder 后，只有节点仍保留对应结果且本地账号与任务关联仍在，才能从轮询重新显示；Sisters 重启、重新部署或淘汰终态历史后可能丢失该入口。删除本地任务、账号或机器会影响关联展示，不影响平台订单。连接失败时可能保留旧结果，应结合获取时间和连接提示判断，不能据此认为旧码仍有效。

## 接入安全核查范围

本轮保留 biliTickerBuy v2.15.18 / `227ebf73f5af3eec0019984a7cbcb722977453e8`，未修改 vendor 快照、导入白名单、依赖锁定或既有下单参数。复核内容包括：

- 取码继续复用下单使用的 `BiliRequest` 和 Cookie；调用目标仍是既有 B 站 `getPayParam`。本地 `payment_qr` 只编码字符，不访问支付链接或新增网络目标。
- 平台请求保持 `standard` 与证书链、域名验证；不引入自制 TLS 客户端。环境代理与 CA 的既有边界仍按[运行时安全约束](biliTickerBuy运行时.md#接入安全约束)说明，不声称强制直连。
- Cookie、购票资料、原始 HTTP 响应和上游错误不随订单信息回传。订单号、支付 token、链接及二维码仅经本机管道、已认证 mTLS 与内存 UI 使用，不能进入普通日志、文件、通知或任意外部 URL。
- 任务结束仍清除排队/运行载荷，不为以后刷新二维码延长 Sisters 保留 Cookie 的时间。
- 第三方通知配置仍为空，Web UI、Gradio 分享和上游启动器仍禁用；二维码生成复用现有依赖，不增加这些服务入口。

## 验证与交付边界

离线验证应覆盖合法与非法支付内容、非法订单号拒绝、伪造详情链接、下单成功但无码、重复订单无码或无 ID、最终结果确认及取消竞态、深拷贝隔离、敏感内容不进事件、mTLS 回传，以及客户端按 UID/订单号去重、未知关联、重复轮询、生成和打开失败、窄屏与大字体布局。本地二维码生成测试使用虚构支付内容，不访问真实订单或执行付款。

2026-11-13 对付款功能的独立源码快照完成以下本地验证：

- `go test -race ./...`、`go vet ./...` 通过，覆盖真实本机子进程取消竞态及本机 mTLS 付款结果回传；取消与协议专项另连续运行 10 轮通过。
- 在锁定运行时依赖就绪的环境中，`python -m unittest discover -s runtime/tests -v` 的 82 项测试通过，无跳过；包括固定取码请求目标、HTTPS 默认验证开启、支付字段脱敏与纯本地二维码编码。付款专项 14 项也使用 Android 打包的二维码/PyPNG 依赖在宿主环境通过，不代表 Android 真机验收。
- `python3 -m unittest discover -s scripts -p 'test_*.py' -v` 的 88 项脚本测试通过。
- `flutter analyze --no-pub` 无问题；`flutter test --no-pub` 为 308 项通过，1 项既有公有云截图用例因未设置可选字体/输出参数按默认条件跳过。付款相关 14 项覆盖去重、时间相同的稳定选码、非法链接与图片响应、生成/打开失败、断线保留、窄屏大字体和迟到图片隔离。
- 另用实际 Flutter 组件和虚构订单生成桌面浅色、窄屏深色预览，检查二维码、文字和操作布局；两个预览中的二维码经本机系统识别器离线解码，与虚构支付内容一致。此结果仅证明这些测试图像的显示与编码，不涉及真实支付链接或支付应用。

本功能的验证范围是源码与离线模拟，不代表全部依赖、各平台发行二进制、真实登录、下单、扫码付款或出票已验收。真实支付内容、有效期、收款信息、浏览器登录与各平台支付应用交互仍需实际订单验证。

此改动尚未发布。使用时须构建包含新版本地运行时和全部同版本 Sisters 部署包的完整 LastOrder，再停止或等待原任务结束并重新部署 Sisters；仅更新 Flutter 外壳或继续连接旧节点不能取得完整付款回显能力。后续发布仍遵守统一版本与全部已支持平台、架构重新打包规则。
