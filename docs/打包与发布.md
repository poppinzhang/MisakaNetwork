# 打包与发布

## 打包方式

Sisters 项目无需单独打包，由于抢票服务的部署均由 LastOrder 完成，因此需要将不同平台、当前版本的 Sisters 服务打包到 LastOrder 中。即使只更新了 Sisters 服务，也需要打包新版本 LastOrder 并升级。

为方便版本管理 和 部署，避免兼容性异常，项目版本号以 LastOrder 为准，部署新版本 Sisters 需要通过升级 LastOrder 再执行重新部署。不再为 Sisters 单独提供版本号。

**所有平台统一版本号，并在每次新增版本号时同步打包。** 发布范围覆盖 LastOrder 和内嵌 Sisters 的所有已支持平台与架构；即使某个平台或模块没有修改，也必须重新生成该版本的完整包，不能跳过打包、保留旧版本号或仅将旧包改名为新版本。这是为简化后续开发与版本管理而接受的额外构建成本。尚未实现的平台继续在发布说明中明确列为限制，纳入支持范围后必须参与每次统一版本打包。

由于 Sisters 使用了 biliTickerBuy 项目，Sisters 需要明确当前使用的 biliTickerBuy 项目版本，这是避免 Sisters 与 biliTickerBuy 不同导致的兼容性问题。在打包时，Sisters 需要将 biliTickerBuy 一并打包到程序中。

原则就是，用户只需要下载 LastOrder 即可完成后续全部部署与任务运行。不需要在后续流程中下载其它任何程序。

## 遵守规则

**1.0.0 之前均为早期研发版本，不承诺向后兼容。** 方案调整优先选择正确性、架构和可维护性更优的实现，无需为旧研发版本保留兼容分支或数据迁移逻辑。允许变更配置格式、接口和行为；发布说明应明确重新登录、重建任务、重新部署等升级影响。

1. 日常改动记在 `CHANGELOG.md` 的 `## unstaged`，分类记录功能、改进、修复和限制。
2. 发布时更新 `pubspec.yaml` 的版本和递增构建号，所有平台共用该版本，并为所有已支持平台与架构重新打包，包括本次没有修改的平台；不要沿用已发布版本号打包新源码，也不要仅发布有修改的平台。
3. 将本次变更放入 `## <版本号>`，记录真实日期、交付状态和已知限制，前面保留空的 `## unstaged`。
4. 按需同步英文和中文 README、新增 `docs/releases/<版本号>.md`；构建仍在等待时明确写“待构建”，不将源码检查、历史结果或未执行的 CI 写成通过。
5. 本地打包产物与核验记录保留在本地 `dist/<版本号>/`；CI 在自己的产物目录生成平台包、独立校验和、联合 `SHA256SUMS` 和 `release.json`，并完成版本、字节数及 SHA-256 自动核验。本地与 CI 产物分别留存，不要求把最终 CI 包下载到本地。执行顺序以下文“每次发布的固定顺序”为准，本节不是提前创建 Tag 的依据。

发布文档、验证记录、日志和产物说明不得记录开发、打包或测试环境的内网地址、机器名、登录账号、SSH 连接信息、个人目录路径、密钥及凭据；只保留必要的通用工具链要求和脱敏结果。临时执行日志不得直接复制为公开发布记录。编译器可能把源码绝对路径写入可执行文件；发行包应从不含个人信息的通用临时源码目录构建，完成后扫描归档及解压内容中的环境隐私标记，再生成最终校验和。

## 工具链与原生运行时

工具链要求：Flutter 3.47.6、Go 1.26、Python 3.11+、Xcode；协议重新生成需要 Protobuf 31+ 和 Go/Dart 插件。依赖版本锁定在 `go.sum`、`LastOrder/pubspec.lock` 和 `runtime/requirements*.lock`。桌面 Python 锁定文件包含 Windows 条件依赖（`colorama`、`win32-setctime`、`pefile`、`pywin32-ctypes`），仅在 Windows 安装；原生安装后运行 `python -m pip check` 验证依赖闭合。

每个平台的 Python 解释器与本地扩展必须在目标系统/架构构建，不能仅交叉编译 Go 后声称完整平台包可用。当前源码五个目标名称为 `linux-amd64`、`linux-arm64`、`macos-amd64`、`macos-arm64`、`windows-amd64`；Windows Sisters 纳入 0.4.0 发布准备，已发布 0.3.2 仍为前四种目标；实际交付状态见 [0.4.0 发布记录](releases/0.4.0.md)。Linux 运行时在 Ubuntu 24.04 同代 glibc 环境构建。macOS 运行时最低部署目标为 15.0。

在对应架构准备隔离 Python 环境后执行（以下以 macOS arm64 为例）：

```sh
python3 -m venv .build/runtime-venv
.build/runtime-venv/bin/pip install -r runtime/requirements-build.lock
.build/runtime-venv/bin/python runtime/build.py --output .build/runtime/macos-arm64
.build/runtime-venv/bin/python runtime/check_bundle.py .build/runtime/macos-arm64/misaka-runtime/misaka-runtime
.build/runtime-venv/bin/python runtime/check_privacy.py .build/runtime/macos-arm64/misaka-runtime
```

`runtime/build.py` 自动复制白名单源码到通用临时目录构建、携带解释器和依赖许可证，并对导入真实引擎的 `ping` 做自检。`check_bundle.py` 只执行离线请求，不登录或下单。`check_privacy.py` 还解开 PyInstaller 压缩代码检查环境路径。

LastOrder「关于」提供离线许可查看入口。依赖、解释器或原生库升级后，按 [开源许可](LastOrder/开源许可.md) 更新补充许可资产；`python3 scripts/collect_licenses.py --check` 及脚本单元测试会校验依赖输入与资产的一致性。此入口不替代发行包随附的许可文件，发布核验仍需对照实际打包组件检查声明。

Linux 可使用提供的 Dockerfile：

```sh
docker build --platform linux/arm64 -f scripts/Dockerfile.runtime -t misaka-runtime-builder:arm64 .
docker run --rm --platform linux/arm64 -v "$(pwd)/.build/runtime:/output" misaka-runtime-builder:arm64 --output /output/linux-arm64
```

对应 x64 将 `arm64` 改为 `amd64`。容器构建允许下载开发依赖；最终用户收到的部署包不依赖这些构建容器。

## 每次发布的固定顺序

1. 更新版本和递增构建号，维护 `CHANGELOG.md` 的 unstaged 项，锁定内嵌 biliTickerBuy 版本。当前集中使用 `0.4.0`、构建号 `13`、biliTickerBuy `2.15.18`。
2. 执行 `scripts/test.sh` 与 `go vet ./...`。新功能相关测试和全部既有测试均通过后才能发布。
3. 按五个目标原生构建运行时，执行离线回归与隐私检查。
4. 执行 `python3 scripts/build_bundles.py`，交叉编译 Sisters（`-trimpath`）并组合五个离线包。产物是内部构建输入，不作为独立 Sisters 发行物发布。
5. 执行 `python3 scripts/build_macos.py` 从临时源码和通用依赖缓存构建 LastOrder，输出 `.build/LastOrder.app`。
6. macOS 分架构执行以下命令（这里只检查 macOS 阶段产物，不能代表完整发布）：

```sh
python3 scripts/package_macos.py --app .build/LastOrder.app --arch arm64
python3 scripts/package_macos.py --app .build/LastOrder.app --arch amd64
python3 scripts/check_release.py dist/0.4.0 --target macos-arm64 --target macos-amd64 --forbid "$HOME" --forbid "$(pwd)"
```

只有 Flutter 应用和框架同时包含所需架构时才能共用同一 `.app`；否则应在目标架构上分别构建。打包器以 `lipo <二进制文件> -verify_arch <目标架构>` 核对应用、Flutter 框架与运行时，避免不同 Xcode 版本将文件路径误解析成架构。包装程序加入本地运行时、部署 helper 与全部五份 Sisters 包，签名检查通过后生成 ZIP。`release.json` 记录文件名、版本、字节数、SHA-256；每个包有独立校验文件，同时生成 `SHA256SUMS`。

7. 按下节生成 Windows 与 Android 完整包；所有平台齐全后执行不带 `--target` 的 `scripts/check_release.py`，拒绝缺包。
8. 在实际应用中验证沙盒下的启动、内置辅助进程及界面；使用 `cmd/misaka-smoke` 对真实 Sisters/运行时进行回环 mTLS 和拒绝非法任务的冒烟验证，不触发真实订单。
9. 更新 `docs/releases/0.4.0.md` 与 CHANGELOG，明确本地、CI、真实平台业务验证各自结果。保留空 `## unstaged`，将已核验内容移动到版本标题。只有完成发布准备后才创建 Tag；本地目录无 Git 仓库时不创建远程发布或 Tag。

## Windows 与 Android 完整构建

0.4.0 的 LastOrder 产物集合为 `macos-amd64`、`macos-arm64`、`windows-amd64`、`android-arm64`、`android-amd64`。Sisters 构建集合为 Linux/macOS arm64/x64 与 Windows x64 共五种；已发布 0.3.2 的 Sisters 仍为四种 Linux/macOS 目标。`windows-amd64` Python 运行时同时用于 Windows 管理台和 Windows Sisters，须在 Windows 原生构建并验证。本次必须按 0.4.0 统一版本重新打包全部目标，不覆盖或复用已发布 0.3.2 的产物。

Windows 构建需要 Windows 10+ x64、Visual Studio 2022 C++ 桌面开发组件、v143 ATL x86/x64 组件（安全存储插件需要）及 Windows SDK，不能在 macOS 交叉编译完整 Flutter Windows 应用。在 Windows 原生环境安装锁定依赖后执行：

```powershell
python -m pip install -r runtime/requirements-build.lock
python runtime/build.py --output .build/runtime/windows-amd64
python runtime/check_bundle.py .build/runtime/windows-amd64/misaka-runtime/misaka-runtime.exe
python runtime/check_privacy.py .build/runtime/windows-amd64/misaka-runtime
python scripts/build_bundles.py --targets windows-amd64
# 汇总其它四种目标后再生成完整索引。
python scripts/index_bundles.py .build/bundles
go test -race ./...
go vet ./...
python scripts/build_windows.py
python scripts/package_windows.py
python scripts/check_release.py dist/0.4.0 --target windows-amd64
```

`build_windows.py` 在通用目录构建并使用独立依赖缓存；CMake 从 Visual Studio 的可再分发目录安装发布版 MSVC 运行库，不复制系统目录或调试版库。`package_windows.py` 核对 PE 版本、EXE 同目录必需 CRT 的 x64 PE 架构、运行时构建清单及全部部署包，再生成便携 ZIP；最终归档校验同样拒绝缺少、错放或错误架构的 CRT。解压整个目录运行 `LastOrder.exe`，不要只拷贝 EXE。Windows 包当前不含 Authenticode 签名。

Android 构建需要 JDK 17、SDK 36、build-tools 36.0.0、NDK 28.2.13676358 和 Python 3.11。Chaquopy 17.1 内嵌客户端运行时，依赖固定在 `runtime/requirements-android.lock`；`build_android_native.py` 在所有主机按 POSIX 清单语义校验路径和上游文件哈希，拒绝盘符、根路径、反斜杠、点目录及符号链接造成的目录逃逸，准备 Python 源码并交叉编译两种 ABI 的 Go JNI 库。构建代码会为 16 KB 内存页设置本地库对齐。`check_release.py` 对 APK 校验进一步检查 Chaquopy/Python 资产、上游模块、锁定依赖版本、CA、嵌套归档内原生库 ELF 与 APK 未压缩库数据偏移的 16 KB 对齐；这些静态检查不替代目标设备运行。完整打包器将五种 Sisters 包置入 APK 原生 assets，不要求设备额外下载。

```sh
python3 scripts/package_android.py --allow-debug-signing
python3 scripts/check_release.py dist/0.4.0 --target android-arm64 --target android-amd64
```

以上命令显式选择测试签名，仅用于本地验证。正式打包时去掉 `--allow-debug-signing`，通过环境变量提供 `MISAKA_ANDROID_KEYSTORE`、`MISAKA_ANDROID_STORE_PASSWORD`、`MISAKA_ANDROID_KEY_ALIAS` 和 `MISAKA_ANDROID_KEY_PASSWORD`，四项必须同时具备。不得将实际路径、口令或密钥写入项目；缺少签名材料时不能把 unsigned APK 称为可安装交付。正式密钥应稳定保管，更换签名会影响覆盖升级。Gradle 不会静默退回测试签名。

运行时每次构建成功后生成 `RUNTIME-MANIFEST.json`，打包必须匹配版本、平台和架构。旧的缓存缺失清单或版本不符时拒绝打包；对于刚构建但尚无清单的运行时，只有在对应原生平台运行 `runtime/build.py --verify-existing <运行时目录>` 并通过实际 `ping` 才能补齐记录，不能单纯编辑清单或重命名旧包。

分平台矩阵产物分别保留自己的 `release.json` 和 `SHA256SUMS`。`release_manifest.py <各平台产物目录> --output dist/0.4.0` 仅在五种 LastOrder 目标全部通过检查后合并。未齐全目录的清单标记 `incomplete` 并列出 `missing_targets`，不能作为已完成统一发布的记录。最终执行：

```sh
python3 scripts/check_release.py dist/0.4.0
```

Android 模拟器与 Windows 原生测试不能由 macOS 单元测试代替。`verify.yml` 的 Android 作业增加 API 36 x86_64 模拟器，执行 `--name 'Android (embedded|JNI|Keystore)'` 过滤后的原生集成测试，覆盖真实 HTTP/2 自检、二维码生成/解码、合成配置生成、JNI 与安全存储；源码作业没有完整部署包，明确排除资源解包用例。使用 `LastOrder/integration_test/android_embedded_test.dart` 可验证 Android 实际 Python/JNI、私有 PKI、安全存储与路径拒绝；完整 APK 还应验证五平台部署资源解包。所有测试使用合成数据，不代表真实登录或下单验收。

## 签名与 CI

当前脚本使用 ad-hoc 签名并保留 macOS 应用沙盒。内置辅助可执行文件使用继承沙盒权限的签名；需要的网络访问与用户选择文件权限由应用声明。Developer ID 签名和 Apple 公证需要发布者证书，不在源码中保存签名材料，本地包尚未公证。

`.github/workflows/verify.yml` 进行源码测试；`package.yml` 保留手动打包入口，并可供 `release.yml` 复用。两者的 Android 作业在构建前先按 `runtime/requirements-android.lock` 建立独立 Python 3.11 环境，断言包含 HTTPX/HTTP2、qrcode 与 PyPNG 且不含 Pillow/Brotli/Zstandard，再运行全部 runtime 测试；桌面依赖包含 Pillow，不能代替这项检查。五平台原生 Sisters 构建后生成 macOS 两种架构、Windows x64 与 Android 两种架构的 LastOrder 包，完整聚合任务依赖全部平台成功。版本和目录从 `scripts/release_config.py` 读取，并与 `pubspec.yaml` 核对；不在工作流中写死版本。

`release.yml` 接收 `<版本号>` 或 `v<版本号>` Tag，先检查发布准备，再构建完整平台集合，最后创建 GitHub Release 草稿、上传白名单中的 12 个必要文件、核验远端大小与 SHA-256 后公开。Sisters 部署包、运行时目录、日志和中间产物只作为短期 Actions artifacts，不进入 Release Assets。Android 正式签名通过 Actions secrets 提供；只有手动 `package.yml` 能选择测试签名，测试 APK 不能进入 Release 发布流程。配置、文件清单、失败恢复与本地验证见 [GitHub Release CI](GitHubReleaseCI.md)。

应用构建任务下载五平台部署包后，执行 `python scripts/index_bundles.py .build/bundles`，校验版本、平台、架构与 SHA-256 sidecar 后原子生成统一 `bundles.json`；Windows 包额外核对两份 x64 PE 可执行文件与运行时版本清单，缺包、错误架构或混合版本不会进入打包步骤。工作流定义不等于实际 CI 通过，实际执行与交付状态见对应版本发布记录。托管 runner 显式扫描本次仓库目录，避免把官方依赖中的通用 runner 主目录构建路径误判为本次环境隐私；本地仍默认扫描个人主目录与仓库路径。Runner 标签参考 [GitHub 官方环境说明](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。CI 包和本地包分别保存与核验。

## 腾讯云模板资源

管理员在完整打包前填写 `LastOrder/assets/cloud_templates/tencent.json`；默认空集合，禁止把演示 ID 当作可购买配置。当前模板格式为 `schemaVersion: 4`，VPC/子网由 LastOrder 自动准备，SSH 用户由模板 sshUsername 指定，22/20001 端口来源固定 `0.0.0.0/0`。模板不再包含 `VirtualPrivateCloud`、`VpcId`、`SubnetId`、`sshCidr` 或 `grpcCidr`；旧格式 1/2/3 需通过新版工具重新生成，不提供兼容读取。该 JSON 已声明为 Flutter asset，Windows、macOS、Android 随应用构建携带同一份内容；修改模板后重新执行所需完整构建。模板校验与参数边界见[腾讯云接入](LastOrder/腾讯云接入.md)，模板填写网页是仓库外的管理员工具，不纳入构建输入或发行包。实际环境参数与秘密不得提交公共仓库；云凭据始终由应用系统安全存储管理，不放模板。

### 阿里云模板资源

`LastOrder/assets/cloud_templates/aliyun.json` 使用 `schemaVersion: 2`，默认空集合。管理员使用仓库外本地配置网页填写并校验，保存模板后重新构建完整应用；Windows、macOS、Android 均由 Flutter assets 携带。模板允许规格、自选 Linux 镜像、登录账号、系统盘和按流量公网带宽，不包含网络 ID、凭据或任意 API 参数。VPC、交换机、安全组与公钥由运行时准备，网页不纳入项目或安装包。详见[阿里云接入](LastOrder/阿里云接入.md)。统一版本与全平台发布要求不变。

### 火山引擎模板资源

`LastOrder/assets/cloud_templates/volcengine.json` 使用 `schemaVersion: 2`，默认空集合；管理员填写后与腾讯云模板一并进入 Flutter assets。模板只支持按量 ECS、单系统盘和按流量 EIP，强制 EIP 随实例释放；不含网络 ID 或凭据。完整打包、版本同步与交付记录规则不变。仓库外填写网页不纳入源码或发行包。具体参数及释放确认见[火山引擎接入](LastOrder/火山引擎接入.md)。

模板编辑器已合并到独立 `MisakaNetwork-config` 工具，默认关联同级主项目，网页源码不进入应用包。镜像完整列表及三家新模板格式和升级操作见[云模板与 Linux 镜像](LastOrder/云模板与Linux镜像.md)。
